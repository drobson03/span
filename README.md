# Span

A workout tracking app with analytics and calendar views. Built with TanStack Start (React), Drizzle ORM, and Neon Postgres, deployed to Cloudflare Workers with [Alchemy](https://alchemy.run).

## Tech Stack

- **Framework:** [TanStack Start](https://tanstack.com/start) (React 19, Vite, SSR)
- **Hosting:** Cloudflare Workers, deployed with [Alchemy](https://alchemy.run) (`alchemy.run.ts`)
- **Database:** PostgreSQL (Neon) through [Cloudflare Hyperdrive](https://developers.cloudflare.com/hyperdrive/), with [Drizzle ORM](https://orm.drizzle.team)
- **Auth:** [Better Auth](https://www.better-auth.com)
- **Styling:** Tailwind CSS v4, Radix UI, shadcn/ui
- **Charts:** Recharts
- **Validation:** Valibot

## Getting Started

### Prerequisites

- Node.js 24.x
- pnpm
- A Cloudflare account holding the `darcyr.dev` zone, and a Neon API key, configured with `pnpm exec alchemy profile edit --add Cloudflare --add Neon` (or `CLOUDFLARE_*` / `NEON_API_KEY` in the environment for CI)
- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in `.env` (see [`.env.example`](.env.example)). They are the only app config that isn't derived or generated

### Stages

`alchemy.run.ts` declares one Worker (`Cloudflare.Website.Vite`) bound to a Hyperdrive connection. URLs come from the stage name and secrets are generated by `Alchemy.Random` and kept in Alchemy state:

| Stage                           | URL                                   | Database                                   |
| ------------------------------- | ------------------------------------- | ------------------------------------------ |
| `prod`                          | `https://span.darcyr.dev`             | The existing Neon project `span` (adopted) |
| `pr-<number>` (CI)              | `https://span-pr-<number>.darcyr.dev` | Copy-on-write branch of production         |
| `live_$USER` (`alchemy deploy`) | `https://span-live-<user>.darcyr.dev` | Copy-on-write branch of production         |
| `dev_$USER` (`alchemy dev`)     | `http://localhost:3000`               | Copy-on-write branch of production         |

- Every stage generates its own `BETTER_AUTH_SECRET`, so no other stage can forge production's sessions.
- `prod` generates the OAuth proxy secret and every other stage reads it from production's state, so `prod` must be deployed first.
- Branches start as a full copy of production data. Previews are public URLs behind the same sign-in as production.
- The production project is retained if `prod` is destroyed. Destroying any other stage deletes its branch, and preview branches also expire after 14 days without a deploy, in case cleanup never runs.

### CI and PR previews

[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) deploys `prod` on every push to `main`, deploys `pr-<number>` for each pull request, and destroys it when the PR closes. Previews are linked from the PR's deployments. PRs from forks or Dependabot never deploy, because they don't receive secrets.

The `production` GitHub environment only deploys from `main`; `preview` is used by preview deploys and cleanup. Both need the same values, so set them once on the repository:

| Name                    | Kind     |
| ----------------------- | -------- |
| `CLOUDFLARE_API_TOKEN`  | secret   |
| `CLOUDFLARE_ACCOUNT_ID` | secret   |
| `NEON_API_KEY`          | secret   |
| `GOOGLE_CLIENT_SECRET`  | secret   |
| `GOOGLE_CLIENT_ID`      | variable |

### First production deploy

```bash
pnpm install
cp .env.example .env   # fill in the Google client

# Adopt the existing Neon project (only needed once)
pnpm deploy:prod --adopt
```

After that, `main` deploys from CI.

### Local development

```bash
# Vite dev server with HMR, connected to this stage's Neon branch
pnpm dev
```

### Schema changes

Migrations live in `migrations/` and are applied by Alchemy on deploy, to the production project on `prod` and to each stage's branch elsewhere. Alchemy records applied migrations in the `__alchemy_migrations` table.

```bash
# After editing src/lib/server/db/schema, generate a migration and commit it
pnpm db:generate

# Try it on your own branch, then open a PR; merging applies it to production
pnpm exec alchemy deploy
```

### Google OAuth proxy

The [Better Auth OAuth Proxy](https://better-auth.com/docs/plugins/oauth-proxy.md) routes local and preview sign-ins through production, so the Google OAuth client only needs `https://span.darcyr.dev/api/auth/callback/google` as its redirect URI. Production sign-ins use the normal flow. The originating environment creates the user and session in its own database.

Production trusts `http://localhost:3000` and `https://span-*.darcyr.dev` to receive those sign-ins, so production must be reachable for local and preview sign-in to work.

### Admins

The [Better Auth admin plugin](https://better-auth.com/docs/plugins/admin) gives users with the `admin` role an **Admin** section in the sidebar, for managing the shared exercise list (`/admin/exercises`) and users (`/admin/users`). Exercises that have been logged can be renamed, but not deleted or switched between reps and timed, since deleting cascades to every user's logged sets.

Admins can promote other users from the users page. To make the first one, set the role in the database:

```sql
update "user" set role = 'admin' where email = 'you@example.com';
```

Each Neon branch is a copy of production, so an admin promoted in production is also an admin on branches created afterwards.

## Scripts

| Command                     | Description                                          |
| --------------------------- | ---------------------------------------------------- |
| `pnpm dev`                  | `alchemy dev`: Vite dev server against a Neon branch |
| `pnpm deploy:prod`          | Deploy the `prod` stage                              |
| `pnpm exec alchemy deploy`  | Deploy a personal `live_$USER` stage using `.env`    |
| `pnpm exec alchemy destroy` | Tear down a non-production stage and its Neon branch |
| `pnpm db:generate`          | Generate a migration from schema changes             |
| `pnpm lint`                 | Lint with Biome                                      |
| `pnpm format`               | Format with Prettier                                 |

## Project Structure

```
alchemy.run.ts     # Alchemy stack: Worker, Hyperdrive, Neon
infra/             # Deploy-time resources (Neon project/branch, Hyperdrive)
migrations/        # drizzle-kit migrations, applied by Alchemy
src/
├── components/    # UI components
├── hooks/         # React hooks
├── lib/
│   ├── client/    # Client-side utilities
│   └── server/    # Server-side code (auth, db, API functions)
└── routes/        # TanStack Router file-based routes
```
